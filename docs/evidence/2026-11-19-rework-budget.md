## 上游依据

Pydantic 团队的 Pydantic AI 将调用实际消耗累计到 `RunUsage`。官方委派测试分别运行共享和独立计量的子 Agent，共享 `ctx.usage` 后，父任务的次数和 token 会包含真正执行过的子调用。其 `UsageLimits` 在下一个模型请求和预计工具调用前检查配置的限制，超限抛出 `UsageLimitExceeded`。官方测试还从已经使用的额度继续运行并验证累计上限。这里沿用共享实际用量和执行前检查的机制。源码与测试均固定到同一提交。[共享计量测试](https://github.com/pydantic/pydantic-ai/blob/6d52359b40e72b643306902b672dc963c660beb5/tests/test_usage_limits.py#L228-L309) · [累计额度和异常测试](https://github.com/pydantic/pydantic-ai/blob/6d52359b40e72b643306902b672dc963c660beb5/tests/test_usage_limits.py#L49-L87) · [请求与工具调用的限额检查](https://github.com/pydantic/pydantic-ai/blob/6d52359b40e72b643306902b672dc963c660beb5/pydantic_ai_slim/pydantic_ai/usage.py#L633-L725)

## Studio 的适配

- 每次派工按群剩余步骤、工具动作、token 和实际墙钟距离截止的时间计算预算。先保留负责人收尾和协调实际后续工作的开销。成员用掉的次数和 token 计回群预算。未设上限的维度贯穿分配和计量。
- 普通派工可以为负责人列出的后续成员留下份额。既有份额最多等于该成员在当前可用余额中的公平份额。如果计入预选角色后当前工作无法入场，就按已承诺的用户义务重算。群成员仅出现在名册上不会占用预算。
- 恢复已保存的私有草稿、处理绑定的评审或复核检查时，优先安排真实待办。用户点名且尚未完成的参与者以及明确子验收仍在计算中。作者返工时另为绑定的独立评审者预留份额，即使该评审者已经签过旧版。授权、冻结候选和修订版的重新签署仍由原评审流程执行。
- 真实可用额度和用户取消决定何时停止。设定有限步数的群任务也可以完成 16 次以上的不同交接，每次实际工作照常扣减。预算不足时，房间记录 `dispatch_budget_exhausted`，包含收件人、实际余量、计算出的成员份额、协调预留和关联评审状态。成功派工沿用 `assignment` 中的 `allocation`、`reserved` 和 `protected_peer_shares`。
- 上述预算计算在 Studio 本地实现，未引入上游依赖或复制上游代码。本文验证的是调度与计量，真实模型事故重跑及原题交付质量需要各自的运行记录。

## 复现与回归

`python -m unittest tests.test_studio_rework_budget tests.test_studio_crew tests.test_studio_peer_checks tests.test_studio_native_review` 使用脚本模型。浏览器重放用例需要可启动的本机 Chromium。

- 从 Studio 服务启动含可选成员的群，初始约 693 秒的 release 份额高于模拟超时后的 425 秒实际余量。验证 dev 能修、原 qa 能签新版、release 能随后完成工作，且负责人始终有 90 秒收尾余量。
- 在有限步数、动作和 token 下验证用户点名、子验收、负责人预留与当前派工的总和。实际余额不足时阻止委派。另用 17 个独立交付和一次复核确认工作可在用户步数预算内继续。
- 原有草稿重试回归继续覆盖未完成的用户子验收、明确接手、真实断言失败和同一人的修复。返工可以使用旧估算留给预选角色的余额。冻结字节和独立签署仍按已有测试逐项核对。
