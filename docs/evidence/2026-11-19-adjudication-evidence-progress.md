# 同一冻结候选上的复核进展

软件题第七轮 `studio-20261119-220017-c5844ebdf0f0` 的候选版本是 `1dc44cad10ac794bc49c03763c9c4c5973f2a405874d9105753d2309a924539f`。原评审的程序在重启后仍请求先前的端口，第 148 行 `assert wait(port)` 失败。独立成员的首次签署保留了同一标准的缺口。它已验证模块中的业务函数；这次签署没有复验失败的重启过程。

后来，这位成员自己的第 23 和 27 步仍各有一次失败。第 28 步在同一份 `app.py` 上实际启动、停止并重新启动服务，沿用相同端口和数据库，使用服务返回的预约编号。它第 116 行的原断言成功，后续检查逐笔验证了取消人、取消时间及重新预约后的记录。第 30 步提交引用拼错，且把未决项一并判为通过。历史运行没有成功签署。把真实回执带入原签署入口可再复现一个独立故障：即使如实提供两次失败和新证据、签 `inconclusive/verification`，宿主仍会因为缺项 ID 相同直接停止。

## 宿主如何记录进展

一个未决的原生 Python 断言可被精确定位到宿主保存的原工具参数及最后一层异常栈。候选 SHA、必需标准、原失败断言位置共同确定覆盖项。独立成员再次运行时，宿主先要求成功断言的回执绑定该标准的冻结产品和必要对照输入，再从当前工具调用的源码与实际 stdout 确认原失败条件、错误标签及后续成功用例。每个冻结的原失败位置只登记一次，拆分任务、换调用 ID、重写日志、追加无关检查、重复失败均不会产生新的覆盖项。运行记录中另存原行、新行与可核对的输出前缀，已有回执 ID 仍可解析。

提取范围包括模块主体及必经的 try/finally 主体，要求后续同段内有明确、唯一且实际输出的用例名称。条件分支、捕获异常的断言、模糊或未观测的结果、不同产品版本等情况保留未决。改写成另一种等价算法时，独立成员仍可依原标准取得证据并签署；宿主无法自动将这两段程序识别为同一个原失败位置。新增覆盖只用于决定是否继续交给同一位裁决者。两次失败的记录保留，任何通过签署都须经过现有候选快照、真实失败、独立角色、预算与发布检查。

覆盖集合的处理参考 coverage.py 的测量模型，通过已执行证据与待覆盖位置取差集；其条件分支和异常路径测试分别展示了未执行分支、清理代码与实际执行路径的差异。Studio 针对短探针使用冻结 traceback 及实际成功用例的取证办法，未引入跟踪依赖。[coverage.py 覆盖集合](https://github.com/nedbat/coveragepy/blob/7.6.10/coverage/results.py#L21-L62) · [不可达分支的回归](https://github.com/nedbat/coveragepy/blob/7.6.10/tests/test_arcs.py#L1470-L1498) · [异常清理路径回归](https://github.com/nedbat/coveragepy/blob/7.6.10/tests/test_arcs.py#L846-L884)

Pydantic AI 的重试节点把可修复的错误送回模型。其工具回归覆盖在失败之间插入无关成功调用仍无法清除那项失败。Studio 采用同样的义务隔离思路，继续复核的条件由已经覆盖的原始位置决定。在提交包含未知或歧义引用时，宿主提示该标准最近的、与冻结产品绑定的真实短 ID，并要求成员核对用途及其余失败。[错误反馈节点](https://github.com/pydantic/pydantic-ai/blob/6d52359b40e72b643306902b672dc963c660beb5/pydantic_ai_slim/pydantic_ai/_agent_graph.py#L4208-L4225) · [交错工具调用的回归](https://github.com/pydantic/pydantic-ai/blob/6d52359b40e72b643306902b672dc963c660beb5/tests/test_agent.py#L1072-L1099)
