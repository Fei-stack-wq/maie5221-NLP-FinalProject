## 2. 用户方向与仍待决定的内容

用户已明确倾向“个人 Agent 工作室”：通过自然语言创建和培养长期角色，赋予或生成 skill，让角色在用户参与下积累经验；统一入口能够选择负责人并组织协作。电脑维护只是示例，底层仍需支持未知评测任务。

前期讨论提出的设计原则，作为本轮接入建议保留：

1. 区分长期角色、项目上下文、会话、任务与执行实例。
2. 同一个角色可以负责多个项目，各项目事实分别保存；重复任务首先增加任务记录。
3. 长期职责与授权关系、单次任务的负责人和委派关系分别表达。
4. 用户可以点名角色，也可以按目标组队；群成员不等于每次任务的执行者。
5. 用户明确偏好、环境事实、操作 skill 使用不同的更新与验证机制。
6. 演化通过有来源、版本和验证的 skill/记忆更新实现；是否改善性能由后续任务衡量。
7. 角色的协调范围与工具权限分别控制；组队、委派或技能更新不会自动扩大权限。
8. 新增项目不必自动创建永久角色；出现持续的跨项目协调责任后再考虑协调角色。

待团队决定：首个演示任务族、持久化后端、运行隔离后端、模块分工、角色管理第一版命令，以及真实模型的验证环境。具体接口和模块名仍是提案。

课程约束继续沿用：仅 DeepSeek/HKGAI（包括路由、反思等辅助调用）、文档输出为 md/txt、极简 CLI、每角色独立记忆与执行边界、HITL、搜索/文件/代码/GitHub 行动、自动成功率和耗时报告。内部结构化状态和源码可以使用 JSON/Python；文档格式限制不能解释成所有任务都只能“写一份报告”。

## 4. 已核实的差距与接入前检查

### 4.1 角色还不是持久身份，skills 还只是路由词

- `AgentCard` 只有 name、skills 字符串列表和 description（`orchestrator.py:52`）。`route()` 优先已有名字，再关键词匹配，最后默认角色（`:155`）。没有项目范围、权限、负责人或生命周期。
- `_build_agent()` 给不同成员使用同一 provider、默认工具集和相同系统提示模板，仅名字不同（`orchestrator.py:625`、`agent.py:37`）。能力卡没有被转换为各角色的执行方法。
- 每次 `Agent.run()` 都重新构造 system + task 历史（`agent.py:104`）。未实现跨 run 的角色存储、记忆检索、skill 文件加载或版本绑定。
- 架构文档里的 `memory.py` 是 P4 计划，仓库中没有这个文件；不能把注释中的“检索/写回记忆”视为已实现。

建议：保留当前 Agent 作为运行实例，增加持久角色配置和上下文组装层；通过已有 factory 生成带角色上下文的运行实例。

### 4.2 依赖只有控制流，没有默认成果数据流

`_execute()` 仅把 `task.objective` 传给新 Agent（`orchestrator.py:575`），没有传入主目标、上游 result、Board 或上游文件。每个子任务又有独立工作目录。因此“研究员先写 sources.md，写作者再据此生成报告”当前缺少默认的交接路径。

`SubTask.acceptance` 自然语言字段虽被保存，默认调用也没有将它加入执行上下文；代码验收是另外通过 `_acceptance_for()` 注入的 callable。

建议：建立显式 TaskContext 和工件交接，传递上游结论、指定文件副本/版本、验收条件和来源。不要直接把所有私有目录挂成一个共享目录。优先补一个“下游必须读取上游实际文件才能成功”的测试。

### 4.3 消息总线还没有形成持续的人机私聊/群聊

MessageBus 有订阅过滤和广播，但默认运行路径主要发布状态与最终 report，没有连接到 Agent inbox，也没有用户输入循环、conversation/team ID 或成员权限。S3 调度使用 `FIRST_COMPLETED` futures（`orchestrator.py:640`），不是依靠 bus subscriber 解锁，`bus.py` 顶部注释应在后续修订中对齐。

总线初始化不加载旧 `bus.jsonl`，history 和序号从头开始（`bus.py:52`）。Board 在整个 run 完成时保存（`orchestrator.py:454`），不是可恢复任务存储。

建议：在总线上增加会话路由与 inbox 接入，保存群成员、消息和等待状态。保留现有审计用途；群成员、执行者与任务负责人分别表达。

### 4.4 HITL 有回调契约，CLI 尚未接上真实人工通道

`RAOUnit._ask_human()` 同步调用 human_handler（`rao.py:559`）；没有 handler 时返回拒绝并让模型继续。CLI 默认传 None，`--yes` 则返回固定的“自行判断继续”文本（`cli.py:214`、`:294`）。目前没有交互式回答入口，也没有 WAITING_USER/checkpoint/resume。

建议：先接通最小真实 CLI 问答，再增加持久等待与恢复。把用户回复、审批和无人值守策略分别处理；不要把预设文本计作用户反馈。依赖用户决定的动作停止，不相关任务可以继续。

### 4.5 目录隔离尚不是课程所需的可靠执行边界

`Sandbox` 对内置文件工具做路径检查。当前编码工具 `run_python` 和 POSIX `run_shell` 在项目目录中以宿主用户权限启动子进程，使用受限的继承环境。Python 额外设置 `-I`。工具层的相对路径与删除审批规则只约束内置文件操作。操作系统级执行隔离仍属于 M0-05。

建议：保留路径检查作为一层防护，增加真正限制文件/进程/网络访问的执行后端。在此之前演示仅使用可控 fixture 和 mock，不连接真实电脑的广泛权限。真实主机诊断需要明确的受控连接器；容器中的命令不能自动代表宿主电脑状态。

### 4.6 默认完成率包含未验证的“软完成”

`evaluate_acceptance(None, ...)` 返回通过（`rao.py:91`）；demo 配了 `accept_files`，普通 run/eval 与默认编排没有强制配置外部验收。`metrics.py` 按 completed 统一计数，没有在摘要里分离软完成。整体目标由所有顶层子任务 done 推出（`orchestrator.py:441`），没有单独整体目标验收。

建议：区分“模型结束”“产物通过验收”“总体目标通过验收”。正式完成率使用明确的验收证据，报告注明软完成；子任务全 done 不自动证明组合后的目标正确。没有验收的结果也不应直接成为“成功经验”。

### 4.7 委派需要先补齐任务身份和预算语义

当前委派会真的执行子 Agent，但采用同步递归（`orchestrator.py:724`）。同父任务、同深度的多次委派使用同一个 `{parent}.d{depth+1}` ID，可能复用目录和覆盖 Board 记录；`parent_id` 已定义但创建 child 时未赋值。子任务未加入顶层 subtasks 集合，关系在最终结果中不完整。

文档提到 `Budget.fork()` 用于嵌套委派预留预算，但默认路径每次新建 `Limits × 0.8` 预算，并没有调用 fork（`:581`）。并行时全局预算在任务结束后扣减，墙钟与子任务累计耗时也应分别表达。

建议：先采用唯一任务 ID、明确 parent/owner/assignee、登记全部委派任务，并统一预算与指标口径。第一版可以仍然同步委派，不必立即改成完整 actor 系统。

### 4.8 真实模型和工具完整度需独立验证

- 此处的初版工具清单是仓库早期基线。当前编码角色可运行 Python 和 POSIX shell、编辑与搜索项目文件，也可使用 `search_sources` 和 `http_get` 查阅外部资料。工具与角色开关以 `build_default_registry()` 为准。
- HKGAI 是预留方向，当前没有单独实现或测试过其适配。
- `_parse()` 与 `LLMResponse.to_assistant_message()` 没有保留 `reasoning_content`（`providers.py:142`、`schemas.py:92`），请求也没有明确禁用 thinking。
- 2026-11-15 查阅的 [DeepSeek 官方 Thinking Mode 文档](https://api-docs.deepseek.com/guides/thinking_mode/) 要求在启用思考且携带 tools 时回传该字段，并说明思考模式默认开启。因此存在多轮工具调用协议兼容风险；这是代码与官方契约对照，**本次未在线复现**。
- 配置错误提示引用 `.env.example`，但当前仓库无此文件；`Settings.from_env()` 读取进程环境，没有加载 `.env` 的逻辑。后续应统一启动说明。

建议先用获准模型验证“工具调用 → 回传结果 → 再调用模型”，再评价自主规划能力。可选择完整支持思考协议或明确配置非思考模式；当前不预先决定。README 旧价格表不作为本次成本结论。

## 5. 工作室对象如何映射到现有模块（提案）

| 新增或扩展对象 | 负责什么 | 与当前代码的连接 |
|---|---|---|
| AgentProfile / ProfileStore | 稳定 ID、显示名、职责、服务范围、偏好、工具策略、技能引用、生命周期 | 从 profile 生成 AgentCard，使用 agent_factory 组装执行者 |
| ProjectContext | 项目身份、资料与配置事实、访问范围、最后验证时间 | 构造任务输入时只取相关项目资料 |
| TaskRecord / TaskStore | 主目标、owner、assignee、parent、依赖、状态、输入输出、验收、预算 | 逐步从 SubTask 和局部 tasks 提升为持久任务记录 |
| ContextBuilder / RunContext | 当前任务、必要记忆、固定 skill 版本、上游成果与约束 | 在 Agent.run 的初始上下文处接入，保持 RAO 执行职责 |
| MemoryStore | 区分用户偏好、环境事实、任务经历；保存来源、作用域与更新记录 | 开始前检索、结束后提交有证据的候选条目 |
| SkillStore | 正文、触发条件、前提、版本、验证记录、发布状态 | 按需加载；任务开始时固定版本 |
| Conversation / Team | 私聊、群成员、默认负责人、消息收件人 | 扩展 MessageBus，连接用户输入与角色 inbox |
| ArtifactStore / Exchange | 带来源、版本、作用域的工件交接 | 从 Observation.artifacts / Board 提取，按授权复制给下游 |

这些对象不要求拆成八个服务。第一版可以保持单进程、简单本地存储接口，先明确所有权和边界，再决定 JSON 或 SQLite。

首轮沿用现有 runtime 和调度器。Hermes、Pi、DeepSeek Harness 可作为方法参考；没有必要为了个人工作室方向立即替换为另一个大型底座。

## 6. 长期关系与任务关系

- 长期关系：角色服务哪些项目、承担哪些持续责任、可以请求哪些能力、资源访问范围是什么。
- 单次关系：当前目标的负责人、任务指派、parent/deps、临时成员和验收责任。
- 拉群从目标出发筛选公开能力卡，先检查项目/工具/权限匹配，再选必要成员。成员身份不自动暴露私有记忆，也不要求每条消息唤醒全部角色。
- 用户创建角色时可以自动建议项目分组与协作者；长期授权变更由用户设置或预先规则决定。
- A 项目的临时小修可以复用已有角色；B 长期独立维护时可建立 B 专员；反复出现跨 A/B 协调工作后，才考虑长期代码协调员。
- 先支持临时助手、项目角色、长期角色及归档恢复。自动升格、自动合并私有记忆和复杂组织学习留作后续。

## 7. 建议的增量里程碑

本节已按后续细化结果更新；具体依赖、接口、验收和首批 PR 以 [分阶段开发计划](agent-studio-development-plan.md) 为准。以下仍是待实施提案。

| 阶段 | 内容 | 完成证据 |
|---|---|---|
| M0 基线可信 | 任务与验收契约、真实 provider、唯一 ID/预算、隔离与授权、工件交接、真实同步人工输入、搜索/GitHub 工具 | 原有有效回归通过，软完成预期随新契约迁移；真实协议、工具与离线结果分别报告 |
| M1 最小个人工作室 | profile 创建/查询/修改/归档；项目上下文；一个版本化 skill 的加载；角色私有事实和偏好持久化 | 重启进程后，同一角色继续使用经过验证的项目信息；A 的事实不混入 B |
| M2 人机协作闭环 | 真实 CLI 私聊/最小群聊；负责人和委派登记；工件传递；用户等待与恢复 | 用户补充约束后相关执行者收到信息；接收者能读取指定上游成果；等待后可恢复 |
| M3 可验证技能演化 | 经验/偏好/事实分流；候选修改→验证→发布→固定版本→回退 | 新案例体现方法复用；旧案例回归通过；版本变化可追溯 |
| M4 评测与提交 | 单角色/固定团队/按需组队，记忆与 skill 消融；冻结评测配置、生成正式报告和提交资料 | 在同模型/工具/总预算下比较成功率、端到端时间、人工等待、重复失败 |

M0 先冻结契约，再并行推进 provider、验收、任务存储与隔离，随后接预算、工件、人工通道和课程工具。搜索与 GitHub 操作提前到 M0，不留到最终评测。真实凭证尚未就绪时可先完成离线开发，但在线项必须明确保持未验收。

## 8. 第一条产品验收故事（建议）

1. 用户创建“小维”，指定维护开发环境、先定位原因、关键操作先询问。资料来自选定项目和可控诊断 fixture。
2. A 项目出现启动错误。小维检查实际入口，发现编辑器和终端解释器不同；修改候选在隔离环境中验证，目标环境是否修复使用独立验收。
3. 用户纠正“先检查实际启动入口”。明确偏好立即保存；项目事实带来源与时间；方法进入候选 skill。
4. 新 skill 至少区分错误解释器、真实缺依赖、应用代码故障三个开发案例；通过后发布固定版本。
5. 重启程序，B 项目出现不同原因的启动错误。小维复用诊断方法，确认是代码问题，再委派代码助手。
6. 代码助手在私有环境中消费指定项目快照，交回补丁与测试证据；小维对整体目标验收。
7. 需要用户决定时任务可保存并恢复。最终记录负责人、角色/项目/任务 ID、skill 版本、验收类型、交接来源和耗时。

这是目标故事，当前仓库还不能完整执行。它同时检验持久身份、用户培养、方法复用、隔离交接和按需协作，避免把“生成了新 skill 文件”直接当作成长。

## 9. 协作开发建议与接手提示

建议按边界分工，而不是按“做一个 manager agent / 做一个 worker agent”分工：

- 角色与成长：profile、项目记忆、skill 版本和验证。
- 协作与会话：TaskStore、工件交接、负责人、消息、HITL 恢复。
- 执行与接入：provider 契约、隔离后端、搜索/GitHub 工具、权限执行。
- 评测与集成：外部验收、离线回归、对照任务集、报告口径。

人数较少时合并这些工作流。`schemas.py` 按仓库现有约定全体 review；跨模块对象先形成共同契约，避免各自定义不兼容的 role/task/skill 结构。后续使用小步分支和提交保留每位成员的持续贡献；M0-01 采用 `jinyuwu/m0-01-contracts` 分支交付。

接手者先执行 `git status --short --branch`，核对本文基线与最新代码，阅读三个已有设计文档和本文，再运行离线测试。第一轮建议先确认 M0/M1 的最小契约与验收故事；实现后在本文或团队选定的同一任务记录中更新实际完成项与验证结果。
